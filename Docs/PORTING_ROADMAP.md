# SwiftBaileys macOS Port Roadmap

## Goal

Build a macOS-only Swift Package that offers an idiomatic Swift API while preserving Baileys protocol behavior.

## Architecture

The Swift package keeps protocol-critical code in small modules that can be verified with fixtures before high-level socket behavior is added. Public API design should use `async/await`, actors for mutable connection state, `AsyncStream` for events, and explicit storage protocols for auth and Signal keys.

- `swift test` passes with JID, `BinaryNode`, raw binary framing, nibble, hex, JID pair, AD JID, single-byte token, and double-byte token tests.
- Earlier fixture generation used the upstream TypeScript checkout; the standalone Swift package now keeps generated resource snapshots and validates them with local Node scripts.
- TypeScript Baileys fixture output for nibble, hex, JID pair, AD JID, representative single-byte tokens, and representative double-byte tokens matches the expected hex embedded in Swift tests.
- `Scripts/verify-binary-token-resources.mjs` validates `Sources/WhatsAppWeb/Resources/Binary/tokens.json` inside the standalone Swift package, so the readiness gate no longer depends on the parent TypeScript checkout.
- `BinaryNodeAttributes` preserves insertion order for byte-for-byte fixture compatibility while equality compares unordered key/value content.
- TypeScript Baileys decode output for FB JID and interop JID fixtures matches the expected Swift decoded nodes.
- TypeScript Baileys decode output for a zlib-compressed binary node fixture matches the expected Swift decoded node.
- `Scripts/generate-wa-proto.sh` validates the required `protoc`/`protoc-gen-swift` tooling, sanitizes proto3 enum zero values in a generated copy, and writes generated sources to `Sources/WhatsAppWeb/Generated/WAProto`. Its `--check` mode regenerates into a temporary directory and compares the output with `WAProto.pb.swift`; `Scripts/verify-production-readiness.sh` runs that check so stale protobuf bindings fail before build/test.
- `WAProto.pb.swift` compiles with SwiftProtobuf and a `Proto_WebMessageInfo` roundtrip test passes.
- The generated `WAProto.pb.swift` file is intentionally large because SwiftProtobuf emits one file per `.proto` input; hand-written Swift files remain under 600 lines.
- SwiftProtobuf is linked through the remote SwiftPM dependency `https://github.com/apple/swift-protobuf.git` from `1.38.0`; `swift package resolve` completed successfully against that manifest.
- `NoiseFrameCodec` covers deterministic Noise frame behavior: intro header once, 3-byte big-endian lengths, multiple frames in one buffer, and partial-frame buffering.
- `NoiseTransportState` covers AES-256-GCM transport encryption/decryption with counter-derived nonces and ciphertext+tag output matching Node/Baileys fixtures.
- `NoiseKeySchedule` covers WhatsApp Noise mode initialization, HKDF-SHA256 mixKey, and empty-input transport key derivation with Node HKDF fixtures.
- `NoiseCurve25519` covers raw X25519 public key derivation and shared secret output using RFC 7748 vectors.
- `NoiseHandshakeState` covers pre-transport transcript hashing, AES-256-GCM with the transcript hash as associated data, HKDF key mixing, counter reset, and ciphertext+tag output matching Node fixtures.
- `NoiseClientHandshakeProcessor` covers Baileys `serverHello` processing against a fixture generated by the TypeScript/libsignal implementation: server ephemeral authentication, two X25519 mix steps, server static decrypt, certificate chain decrypt, client static encryption, and final static-key mix.
- `NoiseClientHandshakeProcessor` now enforces certificate verification decisions before emitting the client static ciphertext: invalid leaf signatures, invalid intermediate signatures, and non-matching issuer serials are explicit handshake errors.
- `NoiseHandshakeState.makeTransportState()` and `NoiseClientHandshakeProcessor.makeTransportState()` derive post-handshake transport keys from empty-input HKDF, matching the Baileys `finishInit()` transition; a Node fixture verifies the first post-handshake ciphertext.
- `NoiseXEdDSAVerifier` verifies a signature fixture generated by `libsignal/src/curve.calculateSignature` and rejects a modified signature. It follows the `curve25519-js` verifier shape: convert Montgomery X25519 public keys to Edwards Y, restore the sign bit from the signature, clear that bit in the signature, then use CryptoKit for the Ed25519 verification equation.
- `NoiseClientHandshakeProcessor` defaults to `NoiseXEdDSAVerifier` while still allowing verifier injection in tests.
- `AuthenticationCredentials`, `AuthenticationKeyPair`, `SignedAuthenticationKeyPair`, `SignedDeviceIdentityAccount`, `SignalIdentity`, and `SignalProtocolAddress` model the Baileys auth credential core needed by the socket without committing generated session state.
- `AuthenticationCredentials.assertMeID()` mirrors Baileys' `assertMeId(...)` auth guard: it returns the authenticated user's JID only when `creds.me.id` is present and non-empty, otherwise it throws a typed missing-user error. Media retry requests now use this shared guard while preserving the existing public client error.
- `SignalKeyStore` stores serialized key blobs by Baileys-compatible category, with an `InMemorySignalKeyStore` for tests and a `FileSignalKeyStore` for macOS persistence. The file-backed store writes `creds.json` plus collision-safe base64url encoded `type-id.json` Signal key files, while still reading and removing the earlier slash/colon-sanitized filenames for compatibility with existing auth directories. `CacheableSignalKeyStore` mirrors Baileys' `makeCacheableSignalKeyStore(...)` boundary with a 5-minute default TTL, cached hit reuse, miss-only backing-store fetches, write-through updates, nil invalidation, and `clear()` propagation. `TransactionalSignalKeyStore` ports the explicit transaction boundary from Baileys' `addTransactionCapability(...)` into a Swift block API with staged reads/writes, rollback on thrown errors, successful commit with retry options, and `AuthenticationState.loadOrCreate(...)` now wraps file-backed Signal keys with cache plus transactions.
- `FileAuthenticationStore` writes credentials and Signal key blobs atomically, creates its directory on demand, enforces `0700` auth-directory and `0600` credential/key-file permissions, reloads persisted state, keeps formerly colliding key ids distinct, and removes key files when nil updates are written.
- `BaileysBufferJSON` ports the byte-object compatibility boundary from Baileys' `BufferJSON`: Swift can now turn `Data` into `{ type: "Buffer", data: "<base64>" }`, read that object shape back, accept legacy numeric byte objects, and pre-normalize TypeScript-auth JSON into regular `Codable` models. `FileAuthenticationStore.loadCredentials()` now uses that normalizer so existing TypeScript/Baileys `creds.json` byte fields can be read without changing Swift's saved credential format.
- `AuthenticationCredentialsFactory` now mirrors Baileys `initAuthCreds()` defaults: identity/noise/pairing/signed-pre-key generation order, pre-key id counters at 1, account sync counter at 0, unregistered state, 32-byte base64 ADV secret, and two-byte masked registration id generation. Production defaults use CryptoKit X25519 key pairs and Security random bytes, while `SignalSignedPreKeySigning` gives native libsignal adapters a public boundary for signing the Baileys signed pre-key payload. The factory rejects non-32-byte Curve25519 key material, non-32-byte ADV secret random output, and non-64-byte signed-pre-key signatures before credentials can be persisted. `SignalSignedPreKeySigning.assertReadyForCredentialSigning()` exposes the same ephemeral signing preflight to app startup code before pairing is enabled.
- `AuthenticationState` now provides a single auth entrypoint with `credentials` and `keys`, matching the shape expected by Baileys sockets. `loadOrCreate(store:credentialsFactory:)` reuses persisted `creds.json` without regenerating keys, or creates and saves new credentials when no auth state exists.
- `AuthenticationState.updateCredentials(_:)` persists successful credential mutations before replacing the in-memory credentials. Tests cover updating registration/user fields and reloading the updated `creds.json`.
- `WhatsAppClient` now optionally owns an `AuthenticationState`, exposes `updateCredentials(_:)`, persists credential mutations through that state, and emits `.credentialsUpdated` with the saved credentials. Lifecycle tests verify in-memory state, persisted `creds.json`, and event emission.
- Incoming `ib/dirty` stanzas now mirror the Baileys socket behavior for account sync, groups, and communities: account-sync timestamps are persisted before cleaning the previous dirty window, groups are refetched before `groups` dirty-bit cleanup, and communities are refetched before the same group dirty-bit cleanup used by the TypeScript socket.
- `WhatsAppBrowserDescription`, `CompanionWebClientType`, and `WhatsAppBrowserPlatform` mirror Baileys' browser helpers for Ubuntu, macOS, Baileys, Windows, appropriate-host defaults, protobuf platform ids, and companion web-client ids. `PairingQRCode.build(...)` produces Baileys-compatible QR data in the form `https://wa.me/settings/linked_devices#ref,noiseKey,identityKey,advSecret,platformId`, and can now derive the QR platform id from a browser description instead of relying on a raw string. `WhatsAppClient.handleIncomingNode(_:)` recognizes `iq type=set` pair-device refs, builds QR data from current auth credentials, and emits `.qrCode`.
- `WhatsAppVersionResolver.fetchLatestBaileysVersion(...)` and `fetchLatestWaWebVersion(...)` mirror Baileys' version-fetch utilities with injectable `URLSession`, bundled fallback `[2, 3000, 1035194821]`, `sw.js` `client_revision` parsing, and the Baileys WA Web request headers.
- When connected, `WhatsAppClient` acknowledges incoming `pair-device` IQ stanzas with a framed `iq` result addressed to `@s.whatsapp.net` before emitting the QR code event, matching the Baileys socket flow.
- `PairSuccessProcessing` defines the injectable boundary for the cryptographic `pair-success` work from Baileys `configureSuccessfulPairing(...)`. `WhatsAppClient` now recognizes `pair-success`, delegates validation/signing to the processor, persists the returned credential update, emits `.credentialsUpdated` and `.newLogin`, and sends the returned reply node.
- `DefaultPairSuccessProcessor` now performs the first `pair-success` validation steps from Baileys: rejecting stanzas that are missing `pair-success/device-identity` or `pair-success/device`, decoding the ADV HMAC protobuf, validating required fields, verifying the account HMAC against `advSecretKey`, and verifying the signed device identity account signature.
- `DefaultPairSuccessProcessor` decodes `pair-success/device-identity` as `Proto_ADVSignedDeviceIdentityHMAC` and maps malformed protobuf payloads to `PairSuccessProcessingError.invalidDeviceIdentityHMAC`, keeping protobuf parser failures behind a typed domain error.
- `DefaultPairSuccessProcessor` validates that the decoded `ADVSignedDeviceIdentityHMAC` explicitly contains both `details` and `hmac` before any cryptographic work, returning `missingDeviceIdentityHMACFields` when either is absent.
- `DefaultPairSuccessProcessor` verifies the Baileys account HMAC contract: `HMAC-SHA256(details, advSecretKeyBase64)` for normal accounts and `HMAC-SHA256([6, 5] + details, advSecretKeyBase64)` for hosted accounts. Tests cover invalid signatures and a valid HMAC path that reaches the next account-signature gate.
- `DefaultPairSuccessProcessor` decodes `ADVSignedDeviceIdentity`, validates required account-signature fields, decodes nested `ADVDeviceIdentity` to choose the normal `[6, 0]` or hosted `[6, 5]` account-signature prefix, and verifies the account signature with the same XEdDSA verifier used by the Noise certificate path. The fixture is generated from Baileys' `libsignal/src/curve.calculateSignature`.
- `LibSignalDeviceSignatureSigner` signs XEdDSA messages with the same deterministic `curve25519-js` path used by Baileys' `libsignal/src/curve.calculateSignature`: clamp X25519 private key, derive the Edwards public key/sign bit, SHA-512 reduce the nonce/challenge, and emit the 64-byte signature. A Swift fixture matches the JS libsignal signature byte-for-byte.
- `DefaultPairSuccessProcessor` builds the Baileys `pair-device-sign` reply through an injected `DeviceSignatureSigning` boundary that defaults to `LibSignalDeviceSignatureSigner`: it signs `[6, 1] + deviceDetails + signedIdentityPublic + accountSignatureKey`, clears `accountSignatureKey` from the response protobuf, preserves the server `key-index`, and returns an `iq type=result` addressed to `@s.whatsapp.net`.
- `PairSuccessProcessingResult` now applies Baileys-compatible credential updates after successful pair success: `me` receives the PN JID, business display name, and LID; `account` stores the signed device identity plus local device signature; `signalIdentities` appends the LID identity with the Signal key bundle prefix; and `platform` stores the paired platform name.
- `WhatsAppClient` now owns a small WebSocket lifecycle abstraction: injectable `WhatsAppWebSocketTransport`, default `URLSessionWebSocketTransport`, explicit connected/disconnected state, binary raw-frame send, and disconnected event emission. Lifecycle tests cover configured URL usage, connect, send, not-connected failure, close, and event emission without reaching the network.

- `WhatsAppClient` starts a receive loop on connect, decodes incoming Noise-framed binary nodes, resolves pending IQ queries through `handleIncomingNode`, and emits `.message` events for unclaimed nodes. Tests feed framed binary data through the mock WebSocket transport without network access.

- `MessageContentBuilder.text(_:)` builds the same `extendedTextMessage.text` WAProto payload that Baileys generates for `{ text }`; the Swift serialized bytes match the `WAProto/index.js` fixture for `"hello from swift"` byte-for-byte.

Tests cover a deterministic Node/Baileys fixture and the production prefix/length invariant.

Tests verify the encoded bytes passed into the encryptor, the final encrypted participant nodes, generated `phash`, explicit `phash` override behavior, and empty-ciphertext rejection.

It rejects empty group ciphertext and rejects empty sender-key distribution bytes when distribution fanout is required.

It remains internal until USync device discovery and Signal session setup can hide device JIDs from the public API.

- `WhatsAppClientMessageDependencies` exposes the outbound Signal/device/media boundaries through the public module API, so a macOS app can plug a production libsignal adapter without relying on `@testable` or internal symbols.

Native adapters can now implement request-based encrypt/decrypt methods directly; SwiftBaileys bridges the older string-based socket calls into validated `SignalProtocolAddress` requests while preserving the original direct-message, group-message, session-check, and sender-key author/group JIDs in the app-facing native DTOs.
- `WhatsAppComposedNativeSignalBackend` gives macOS apps a public composition path when persistent native Signal state and libsignal crypto live in separate objects. `WhatsAppNativeSignalStore` owns account import/checking, session install/checking, and pre-key upload state, while `WhatsAppNativeSignalCryptoProvider` owns signed-pre-key signing, operation readiness, direct/group encryption, incoming decryption, and sender-key distribution processing. The composed backend still conforms to `WhatsAppNativeSignalBackend`, and `WhatsAppNativeSignalBackendAdapter(store:cryptoProvider:)` exposes the common direct adapter wiring for apps that do not need to hold the composed backend separately.
- `AuthenticationCredentialsFactory(nativeSignalAdapter:)` lets macOS apps use the same `WhatsAppNativeSignalAdapter` for initial credential signed-pre-key signing instead of wiring a separate signer object.
- `AuthenticationCredentials.nativeAccountKeyMaterial()` exposes a validation-backed `SignalNativeAccountKeyMaterial` for native libsignal store bootstrap immediately after auth load/create, independent from later low-pre-key recovery. It rejects malformed raw Curve25519 public keys, signed-pre-key signatures, and signed-pre-key ids outside WhatsApp's 3-byte key-id range before app-owned stores receive account material. ## Implementation Order

1. Keep the existing TypeScript package untouched and develop the Swift rewrite under `SwiftBaileys/`.
2. Build protocol primitives first: JID, `BinaryNode`, binary encoder/decoder, protobuf generation.
3. Add cryptographic transport: Noise, frame encryption, and Signal bindings.
4. Add `AuthStore`, `SignalKeyStore`, and file-backed macOS storage.
5. Add socket lifecycle and IQ request/response handling.
6. Add message receive/send, then media, then the remaining Baileys feature areas.

## Non-Negotiables

- Do not invent WhatsApp stanza details. Every protocol change needs a fixture, existing TypeScript source reference, or captured test input.
- Do not hand-edit generated protobuf files.
- Do not reimplement Signal cryptography from scratch.
- Do not commit auth/session state.
- Keep Swift files below 600 lines.
